# Сохранение соединений при сбое проверки готовности БД

В первом параллельном Linux-прогоне тестовая PostgreSQL сообщила о дочернем процессе, вышедшем с кодом 2, начала восстановление и оборвала запрос теста. Повторный изолированный прогон прошёл, но сам по себе не объяснял отказ.

## Воспроизводимый дефект конфигурации

Без отдельного init-процесса `postgres` работает как PID 1 контейнера. Он получает осиротевшие процессы, в том числе потомков завершившегося shell из healthcheck. Если такой процесс выходит с кодом 2, обработчик дочерних процессов PostgreSQL трактует это как сбой backend и сбрасывает рабочие соединения. Сообщение «server process» поэтому не доказывает, что завершившийся процесс обслуживал SQL-запрос.

Механизм согласуется с [CleanupBackend в исходниках PostgreSQL 17](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/postmaster/postmaster.c) и [ранее разобранным случаем в Super Productivity](https://github.com/super-productivity/super-productivity/issues/9695). Здесь он проверяется собственным сценарием на том же образе PostgreSQL 17.12, который использует проект.

Для PID из первоначального прогона не сохранился `/proc`/trace процессов, поэтому его конкретная принадлежность healthcheck остаётся выводом по совпадающему механизму. Сам дефект конфигурации воспроизводится независимо от этой исторической атрибуции.

## Регрессия

```bash
python3 scripts/check_db_reaping.py
```

Скрипт использует только `db` из `compose.test.yaml` в отдельном проекте с префиксом `stackbridge-db-reaping-` и случайным суффиксом для каждого запуска. Если такое имя уже существует, скрипт отказывается его менять. После проверки созданные им контейнеры и сеть удаляются; БД приложения не используется. Очистка проекта выполняется и при ошибке завершения процесса постоянного соединения; исходная ошибка проверки при этом сохраняется. Эти ветви проверяют `tests/test_deployment_cleanup.py`.

Последовательность:

1. Дождаться готовности окончательного сервера по TCP, минуя временный Unix-only сервер `initdb`.
2. Открыть постоянное SQL-соединение; advisory lock подтверждает его готовность и позволяет определить PID backend.
3. Создать фоновый процесс проверки с файловым барьером, завершить его родительский shell и проверить `PPid=1`.
4. Отпустить барьер: настоящий `pg_isready` обращается к закрытому порту и возвращает код 2; обёртка сохраняет и возвращает тот же код.
5. Проверить, что исходное SQL-соединение сохранилось, PID backend остался тем же, а журнал не объявил PID проверки аварийным backend.

До исправления сценарий воспроизвёл восстановление PostgreSQL и завершение постоянного соединения с кодом 2. Первоначальная версия проверки по `pg_postmaster_start_time()` оказалась недостаточной: при восстановлении shared memory основной postmaster остаётся жив. Проверка заменена наблюдением за постоянным соединением и журналом конкретного PID до изменения конфигурации.

## Исправление

В `db` обоих Compose-файлов включён `init: true`. Согласно [документации Docker Compose](https://docs.docker.com/reference/compose-file/services/#init), отдельный PID 1 передаёт сигналы и освобождает завершившиеся процессы. Осиротевшая проверка теперь попадает к этому процессу, а PostgreSQL обрабатывает только собственных детей. Сценарий не меняет ожидания HTTP-тестов и не повторяет упавшие утверждения до успеха.

Эта регрессия также включена в CI перед полным набором тестов. Фактические результаты RED/GREEN и полного прогона фиксируются в [verification.md](verification.md).
