Это окончательный прогон после исправления жизненного цикла БД и замечаний ревью. История первоначального отказа и отдельная реальная контейнерная регрессия приведены ниже.

## Проверка чистой Ubuntu

Для проверки создана отдельная виртуальная Ubuntu 24.04 на QEMU в рабочей папке. Официальные образы QEMU и Ubuntu проверены по опубликованным SHA-512/SHA-256. QEMU распакован без установки в Windows; системная перезагрузка или замена окружения пользователя не выполнялась.

На первоначально чистой Ubuntu скрипт действительно установил Docker Engine/Compose из официального репозитория, собрал runtime с FFmpeg и загрузил PostgreSQL 17/SeaweedFS 4.44. Первая попытка выявила два дефекта конфигурации: файл S3 credentials был недоступен UID образа, а рост томов по умолчанию исчерпал заданные пять слотов до первой записи в S3-коллекцию. Исправлены права bind-файла при закрытом родительском каталоге и рост по одному тому с автоматическим расчётом числа слотов.

После исправления `bash start.sh` завершился успешно: initialize вышел с кодом 0, web стал healthy. Real-stack HTTP smoke прошёл внутри Ubuntu: загрузка → отдельный FFmpeg worker → MP4/JPEG, Range, разрешение/отзыв доступа, общение, плейлист и удаление тестового контента. Дополнительная проверка настоящего S3 подтвердила подписанный доступ и `403` на анонимный GET существующего объекта.

VM использует 2 ГБ RAM и два программно эмулируемых CPU; рекомендуемая среда проекта — от 4 ГБ. Измеренная задержка готового `/healthz` в этой VM составила 4,5 секунды, а запуск Python-проверки превышал прежний лимит 5 секунд. Таймауты готовности увеличены до 20 секунд на процесс/10 секунд на запрос, ожидание Compose — до 600 секунд. Это ограничение медленной программной эмуляции; оно не выдаётся за нагрузочный тест.

Отдельная установка в новом Compose-проекте `stackbridge-fresh`, с новыми секретами и пустыми named volumes, завершилась успешно: 10 demo users, 12 videos, два логических тома SeaweedFS. `start.sh`, HTTP smoke и проверка signed/unsigned S3 прошли. Повторный `start.sh` также прошёл: количества users/videos/playlists/comments до/после совпали, SHA-256 `.env` сохранился; HTTP smoke и signed/unsigned S3 снова прошли.

Первый полный контейнерный прогон дал **39 passed / 1 failed** за 594 секунды. Единственный отказ — `test_invalid_ranges[bytes=-0]`: ошибка подключения SQLAlchemy/psycopg во время восстановления тестовой PostgreSQL, до проверки самого Range. Лог PostgreSQL показывает выход одного дочернего процесса с кодом 2 и восстановление postmaster; OOM в журнале ядра не обнаружен, место в tmpfs и `/dev/shm` оставалось. Причина выхода процесса не установлена. Основная БД приложения и native preview были отдельными и не перезапускались. После остановки соседнего проверочного стека повторный полный прогон дал **40 passed in 242.43s**, код завершения 0; неожиданный перезапуск БД не повторился. Код приложения, таймауты и утверждения тестов между этими прогонами не менялись. Успешный повтор не объявляется установленной причиной или исправлением первоначального выхода процесса.

## Продолжение: жизненный цикл контейнера PostgreSQL

После просьбы пользователя продолжить работу воспроизведён конкретный дефект: при PostgreSQL в роли PID 1 осиротевший процесс проверки готовности с кодом выхода 2 вызывает восстановление БД и обрывает постоянное SQL-соединение. В RED совпали PID специально созданной проверки и PID в сообщении PostgreSQL о сбое; соединение завершилось с кодом 2. До изменения Compose ошибочный критерий по времени старта postmaster был заменён наблюдением за постоянным соединением: postmaster при таком восстановлении остаётся жив.

У `db` в обоих Compose-файлах включён `init: true`. В GREEN PID 1 — docker-init, PostgreSQL — PID 7; осиротевшая проверка также вышла с кодом 2, но то же SQL-соединение сохранилось. После независимого ревью исправлены гарантированная очистка диагностического проекта и конфликт имён параллельных запусков; три fault-injection теста сначала дали RED, затем GREEN. Окончательная реальная регрессия с уникальным именем проекта тоже прошла, после неё полный Linux-набор дал 43/43. Разбор и команда воспроизведения — в [database-readiness.md](database-readiness.md).

В отдельном новом проекте `stackbridge-db-fix` проверены запуск приложения с init, настоящий upload/FFmpeg/playback/S3, затем штатный перезапуск БД. Количества пользователей и видео сохранились, SHA-256 `.env` совпал. После перезапуска без замены web/worker повторно прошли HTTP smoke и signed/unsigned S3. Подтверждён воспроизводимый механизм дефекта; точную принадлежность PID 743 из первого исторического сбоя без утраченного снимка процессов установить нельзя.

Промежуточный нативный запуск в ограниченной Windows-песочнице завершился ошибкой доступа к временной папке pytest/FFmpeg и не считается успешным. Окончательный нативный прогон выполнен в обычном локальном окружении с отдельной тестовой БД и новым рабочим временным каталогом; результат — 43/43. Исходные утверждения API-тестов и их ожидания ради успеха не менялись.

## Комплект диалогов

Исходный ZIP распакован отдельно: `git fsck --full` прошёл, working tree чистый, remote отсутствует. Проверены хеши всех 360 файлов в 16 снимках скиллов. Локальные секреты, runtime и нативные JSONL исключены из этого ZIP; `.env`/runtime не встречаются в истории Git. Исходный репозиторий сохранён на локальной ветке `implementation` с последовательными коммитами. Пользовательское native preview отвечает `200 {"ready":true}` на `/healthz`.

Нативный журнал существует. Он содержит внедрённый платформой контекст других проектов/идентификаторы аккаунта. По явной команде пользователя полный оригинал сохраняется отдельным локальным архивом для его проверки. В исходный ZIP он пока не включается. До решения пользователя формальное требование ТЗ о диалогах в общем ZIP остаётся открытым; поддельный или очищенный лог за оригинал не выдаётся.
